Is a browser extension safe for 2FA codes? How Popout Authenticator stores your secrets

This page describes what Popout does with the secret key behind each code: where it is kept, how it is encrypted, what leaves the extension, and which risks remain. Every statement here comes from the extension's source code, which is open.

Where the secret keys are kept

  • All accounts, including their secret keys, are stored in one vault in the extension's local storage (chrome.storage.local, key vault). The vault is a single encrypted block, not one entry per account.
  • When you unlock the vault, its key is held in the extension's session storage (chrome.storage.session) so you are not asked again until the auto-lock time you chose. It is not written to local storage.
  • Earlier versions of the vault are kept as backup history in the browser's IndexedDB database (popout-authenticator). Popout keeps the latest 30, plus the most recent one for each of the last 30 days. When you turn the lock on, those older versions are re-encrypted with the new key.
  • The sites you turned on for the "Fill code" button are stored as plain site addresses next to the vault. They contain no secret keys.

How they are encrypted

Popout uses two layers, so that changing your password does not mean re-encrypting every account.

LayerWhat it is
Vault keyA random 32-byte key, generated on your device. It encrypts the whole account list with AES-256-GCM, using a fresh random 12-byte value for each save. A SHA-256 checksum of the stored data is kept alongside it.
PasswordYour password is stretched with Argon2id (3 passes, 64 MiB of memory, 1 lane, a random 16-byte salt) into a 32-byte key. That key encrypts the vault key. The password must be at least 8 characters.
Recovery codeIf you create one, a second copy of the vault key is encrypted with a key derived from the recovery code (HKDF-SHA256).
PasskeyIf you add one, a further copy of the vault key is encrypted with a key derived from the passkey's PRF output (HKDF-SHA256). It is used together with the password.

See Lock and protect your accounts for how to set the lock and its timing.

With no lock set

If you do not set a lock, the vault is still encrypted with AES-256-GCM, but the vault key is stored next to the encrypted data in the same place, without a password around it. Anything that can read the extension's storage can read the key and decrypt the accounts. Treat this state as unencrypted. It does not protect your secret keys from someone who can open your browser profile.

Setting a lock changes this: the vault key is then stored only in its encrypted form, and your password (or recovery code) is needed to unlock it. Check in the lock settings which state you are in.

What leaves the extension

  • Popout generates codes on your device from the stored secret key and the clock. Generating a code makes no network request.
  • The only network request in the extension's code is an optional clock check. It makes plain GET requests to time.akamai.com, timeapi.io, and cloudflare.com to compare your computer's clock with real time, because a wrong clock produces wrong codes. The requests carry no account data and no body. The result is reused for 6 hours when the clock is right, and re-checked after 5 minutes otherwise. As with any web request, those hosts see your IP address. The check is on by default and can be turned off in settings.
  • There is no analytics, usage statistics, account sign-in, or developer-run server in the extension.

Browser sync

  • If sync is on, Popout writes each account, encrypted with AES-256-GCM, to the browser's own sync storage (chrome.storage.sync). Your browser vendor's sync service then carries it between your devices. Popout does not run a sync server.
  • By default Popout syncs only after you have set a lock. Syncing without a lock needs a separate choice, "Allow syncing without a lock". Because the vault key is stored in clear when no lock is set (see above), this setting sends accounts that anyone with access to the synced data could read. The Firefox build also asks for its data-collection permission when you turn sync on.
  • The Safari build has no cross-device sync.
  • See Backup, export, and sync for the steps.

Permissions it asks for

These are the permissions in the extension's manifest. The reasons are the ones listed in the project README.

PermissionWhy
storage, unlimitedStorageKeeps the vault, settings, and backup history on your device; the second one avoids the default storage quota for that history.
activeTab, scriptingFills a code into the current tab and reads a QR code on it, only after you click, right-click, or use a shortcut.
alarmsAuto-lock, periodic sync, clipboard clearing, and cleanup timers.
contextMenusThe "Fill 2FA code" item on input fields and "Open in a separate window" on the toolbar icon.
clipboardWriteCopies codes, share links, and recovery codes.
offscreen, sidePanel (Chrome, Edge)Clearing a copied code from the clipboard after the time you choose, and opening the side panel.
tabs, clipboardRead (optional)Asked only when needed: the first lets the separate window and side panel suggest an account for the active tab's site; the second is requested only when you turn on clipboard clearing.
Site access: https://*/*, localhost, 127.0.0.1 (optional)Not granted at install. Popout asks for it only for the sites involved: the current site when you fill from the separate window or side panel, the sites you enter for a "Fill code" button, or a fixed list of known services if you turn on automatic recognition. It never asks for all sites at once.

The manifest declares no site access that is granted at install. All of it is optional and requested later, as described in the last row.

Backups and share links

  • A plain backup file is readable: it contains your secret keys in clear text. Keep it like a password, or choose an encrypted backup, which uses Argon2id and AES-GCM with a password you set.
  • A share link contains only upcoming codes, not the secret key. It is built on your device; the data is in the part of the address after #, which browsers do not send to the page's server. A link without a password can be opened by anyone who has the link. A link with a password is encrypted with a key derived from that password (PBKDF2-SHA256, 600,000 iterations). See Share a code with a link.

What it cannot protect against

These limits come from where the data lives, and no setting removes them.

  • Malware or a hostile program under your own account. Something running as you in the same browser profile can read what the extension can read, and can watch the unlocked state. A lock helps only while the vault is locked.
  • No lock, and access to your files. Without a lock, someone who can copy your browser profile folder can read the accounts, as described above.
  • A backup file in the wrong hands. A plain backup works for whoever holds it. Where you store it is up to you.
  • A copied code. A copied code sits on the system clipboard, where other programs can read it. Automatic clipboard clearing is off by default; you can turn it on.
  • A weak or reused password. Argon2id slows down guessing, but it cannot make a short or common password strong.
  • Filling on the wrong site. Popout checks the page address before it fills and asks if the site does not match (Site match check), but you still decide when it asks.

A phone app keeps its data outside the browser, on a different device. A browser extension keeps it inside the browser profile on the computer you are using. They have different risks, and this page describes only Popout.
